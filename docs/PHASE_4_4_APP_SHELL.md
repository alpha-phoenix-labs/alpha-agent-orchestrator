# PHASE 4.4 — App Shell

Status: **PATCH PREPARED — READ-ONLY UI SHELL**

Baseline: `main@3ea353b8cdf2ce84e852600e6578cd9a8b88a00e`

## Purpose

Phase 4.4 creates the common Operations Console shell required by frozen-roadmap section 7.4 without pulling Phase 4.5+ domain views forward and without adding any operational write surface.

The shell provides:

- a global header;
- the required primary navigation;
- an Active Context Bar;
- client-side routing;
- route-level error isolation;
- a minimal typed data/state boundary for authoritative backend view contracts.

## Frontend baseline

Phase 4.3 selected the initial frontend stack after confirming that no frontend already existed in the repository. Phase 4.4 initializes that selected stack under `frontend/`:

- React;
- TypeScript;
- Vite;
- React Router;
- Tailwind CSS;
- Vitest;
- React Testing Library;
- user-event;
- npm with a committed lockfile;
- Node.js 24 for CI/tooling.

The dependency graph is pinned by `frontend/package-lock.json` generated by npm rather than handwritten.

## Navigation contract

The primary navigation matches the frozen-roadmap target exactly:

- Mission Control — `/`;
- Work Orders — `/work-orders`;
- Evidence & Audit — `/evidence-audit`;
- System / Swarm — `/system-swarm`.

Phase 4.4 route bodies are intentionally placeholders. Mission Control and subsequent domain surfaces remain in their own roadmap phases.

## Active Context Bar

The Active Context Bar consumes only the typed UI-side representation of the Phase 4.2 view-contract wire shape.

The source-class vocabulary remains exactly:

- `AUTHORITATIVE`;
- `WORK_ORDER`;
- `EVIDENCE`;
- `RUNTIME`;
- `TELEMETRY`;
- `LOCAL_UI`.

The app shell does not synthesize authoritative state. With no backend snapshot supplied, it renders:

- authority: `UNAVAILABLE`;
- system mode: `UNKNOWN`;
- repository: `UNKNOWN`;
- canonical state: `UNKNOWN`.

This is deliberate fail-closed behavior. Local UI state is not permitted to replace backend authority.

## Error isolation

The shell includes an error boundary around routed content. A route failure is rendered as an isolated unavailable view and explicitly does not imply system authority, write eligibility, approval state or writer state.

No error transport or telemetry backend is introduced here; those belong to later observability/runtime phases.

## Accessibility and motion baseline

The shell includes:

- semantic primary navigation;
- visible focus treatment for navigation links;
- an accessible label for the Active Context Bar;
- explicit textual `UNAVAILABLE` / `UNKNOWN` state rather than color-only status;
- reduced-motion handling through `prefers-reduced-motion`.

This is a baseline only; the full Phase 4 accessibility gate remains governed by roadmap section 7.15.

Backend job remains the existing Python control-plane regression path.

Frontend job uses Node.js 24 and executes:

1. `npm ci`;
2. `npm test`;
3. `npm run build`.

## Security properties

Phase 4.4 intentionally does **not** add:

- a backend endpoint;
- WebSocket, SSE or another live-event transport;
- a writer trigger;
- approval controls;
- capability minting or capability display;
- deploy controls;
- merge controls;
- lock override controls;
- force actions;
- secret input or secret rendering;
- frontend authority over policy, gates, locks, freshness, Evidence verification or canonical state.

No productive deploy is part of this patch.
